# Precision P10 Canary / Cutover Gate v1

P10 binds a P9 MANUAL_REVIEW_CANDIDATE to the repository's existing manual-canary and production-routing contracts. It does not create a trusted production approval and it does not switch production traffic.

Flow:
P9 MANUAL_REVIEW_CANDIDATE -> one-target dry-run canary template -> fresh runtime-preimage materialization -> human approval -> isolated canary -> rollback rehearsal -> AWAITING_TRUSTED_PRODUCTION_APPROVAL -> separate production routing cutover gate.

P10 adapter invariants:
- P9 bundle must have production_write_allowed=false and automatic_live_promotion=false;
- exactly one resident role/layer may change;
- target old_n/new_n must match baseline and proposed policy;
- both G4 A/B/R and G6 restart-canary evidence remain mandatory in the existing manual-canary contract;
- a passing canary alone is insufficient: a ROLLBACK_VERIFIED rehearsal is also required;
- P10 output remains production_cutover_allowed=false;
- no trusted approval is generated by P10;
- existing production_routing_cutover still requires a separately verified GitHub OIDC approval bound to the exact cutover-plan SHA.

Current boundary:
The historical L3 P8/P9 candidate still lacks replay provenance, so no real P9 MANUAL_REVIEW_CANDIDATE exists yet. P10 therefore does not launch or mutate a production canary. The gate is ready for the first future provenance-backed P9 candidate.

Regression: P10/manual-canary/routing focused 49/49 PASS; GPU suite 230/230 PASS.
