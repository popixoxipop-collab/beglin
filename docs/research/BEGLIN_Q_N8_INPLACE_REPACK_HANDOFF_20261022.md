# BEGLIN Q — qNg64 n8 in-place repack + Apple NEON full-model 검증 핸드오프

작성: 2026-10-22 KST · 연구 브랜치 `research/oml-acs-prereg-20261021`

**결론:** 실제 Qwen2.5-1.5B의 BF16 원본 가중치를 BEGLIN qNg64 n8로 변환한 뒤, 8개 비트플레인을 매 GEMV마다 해제하는 대신 **각 64개 그룹을 최초 로딩 때 한 번만 64바이트 signed INT8 코드로 제자리 재배열**하여 읽는 커널을 구현했다. 원본 전체 BEGLIN이나 운영 바이너리를 바꾸지 않은 격리 연구용 Apple CPU 테스트에서 **동일한 모델 로짓·PPL을 유지하면서 전체 8비트 디코드는 이전 NEON보다 1.52배, 최초 스칼라보다 13.87배 빨라졌다.** 8비트 28개 + 4비트 168개의 두 기존 혼합 정책에서도 이전 NEON보다 약 24% 빨랐다.

## 1. 왜 성능이 개선됐는가

- 이전 qNg64 n8 압축: 64코드당 8개 bitplane × 8바이트 = 64바이트. NEON 경로는 매 토큰·매 텐서마다 8개 비트플레인을 펼쳤다.
- 새 연구 경로: 각 그룹 64바이트를 먼저 stack 64바이트 임시 버퍼에 전부 해제해 **원본 packed malloc 64바이트 자리에 그대로 덮어쓴다**. 이후 NEON 연산은 연속된 INT8 코드로 바로 연산하므로 비트 추출 반복이 사라진다.
- **압축 가중치의 바이트 수는 그대로** 유지한다. on-disk HF BF16 및 원래 qNg64 bitplane 파일 형식은 변하지 않는다. 단, **실행 중 메모리 값의 의미는 bitplane에서 signed code로 바뀌므로 같은 포인터를 원본 디코더에 다시 전달하면 안 된다.** 정식 통합 전에 명시적인 layout/kind 태그, 버전 검사, 로더별 fail-closed 분리가 필요하다.
- 새 전체 모델 연구 바이너리는 original C 소스를 SHA로 고정한 이전 연구 복사본을 입력으로 삼았다. 원본 qNg64를 함수 이름만 변경해 보존하고, 연구용 n8 전용 GEMV와 M>1 배치 경로를 별도 link wrapper로 제공한다. 다른 qNg64 폭은 원본 스칼라 경로를 유지한다.

## 2. 실제 가중치와 Apple CPU 단일 텐서

Qwen2.5-1.5B `model.layers.0.self_attn.q_proj.weight` (1536×1536)와 원래 BF16 임베딩에서 만든 96개 입력을 사용했다. 7~9회 반복한 단일 텐서 벤치마크의 중앙값:

| 원래 스칼라 | 이전 실시간 NEON bitplane 해제 | 새 1회 재배열 NEON |
|---:|---:|---:|
| 8.859 ms/벡터 | 0.918 ms/벡터 | **0.566 ms/벡터** |

- 스칼라 대비 **15.66배**, 이전 NEON 대비 **1.62배**.
- 2,359,296바이트 n8 가중치 재배열에 약 **2.14ms**, 이전 NEON 대비 이득으로 약 6.1개 벡터 연산에 초기 비용 회수.
- 96개 벡터 출력: 원래 스칼라 대비 최대 절대 오차 **7.63×10⁻⁶**, 상대 L2 오차 **3.74×10⁻⁸**.
- 다른 실제 BF16 텐서 4형태 `(256,1536), (1536,1536), (8960,1536), (1536,8960)`로 독립 반복: **14.85~15.31배 스칼라 대비 속도**, 최대 출력 절대 오차 **2.98×10⁻⁸**, 동일 n8 code 바이트 수.
- 배치 3개 입력의 원래 n8 스칼라 vs 연구 batch wrapper 최대 절대 오차 **3.81×10⁻⁶**. 다른 qNg64 폭 n=3,5,6,7은 원본 batch와 출력 **bitwise 동일**함을 확인했다.

## 3. 실제 BEGLIN 전체 Qwen 28계층 검증

세 경우 모두 **같은 BF16 원본 Qwen2.5-1.5B 고정 리비전**, 같은 151,936 어휘/공개 합성 10-token 입력, 같은 21개 위치의 PPL 평가, 동일 FP32 tied head, 기존 텐서 할당 정책 유지. n8 code 버퍼만 새 표현으로 바꿨다.

| 전체 모델 | 이전 스칼라 | 이전 NEON | 새 1회 재배열 | 이전 NEON 대비 |
|---|---:|---:|---:|---:|
| 196개 전체 n8 | 0.190 tok/s | 1.732 tok/s | **2.638 tok/s** | **1.52배** |
| 무작위 혼합 28 n8 + 168 q4 | 1.233 tok/s | 6.951 tok/s | **8.607 tok/s** | **1.24배** |
| 오차 기반 혼합 28 n8 + 168 q4 | 1.234 tok/s | 6.924 tok/s | **8.607 tok/s** | **1.24배** |

- 새 전체 n8 379.06ms/토큰, 기존 원본 스칼라 5257.63ms/토큰 대비 **13.87배**.
- 새 혼합 2종 116.18ms/토큰. 기존 전체 q4 6스레드 75.26ms/토큰(13.29tok/s)보다는 여전히 **느리다**.
- 전체 n8, 혼합 무작위, 혼합 오차 기반의 최종 **151,936 로짓 출력은 각자 이전 on-the-fly NEON 버전과 파일 SHA까지 완전히 일치**했다. 실제 모델 출력의 기존 n8 스칼라 대비 Top-10도 10/10 동일.
- 각 전체 모델의 PPL: **2148.1231 / 3411.2283 / 4747.6983**, 이전 NEON과 동일. 비공개 synthetic 원문/텐서는 공개하지 않았다.
- 최대 PPL 프로세스 RSS: 전체 n8 **5.49GB**, 무작위 혼합 **4.923GB**, 오차 기반 혼합 **4.922GB**. 일회성 제자리 코드 재배열로 모델 가중치 크기 증가 없음.

- **측정 한계:** full-model tok/s는 기존 BEGLIN `bench 1`의 워밍업 후 *3회 중 최단 단일 토큰* 결과이다. 장시간 연속 TPS, 병렬 작업, 에너지, Metal GPU 측정이 아니다. PPL도 공개 합성 21개 토큰에 국한. 전체 BF16 연산은 테스트하지 않았으며 원본 BF16 가중치를 FP32로 승격한 기준만 있다.

## 5. 다음 단계

1. 정식 BEGLIN 통합을 검토한다면 먼저 로더·텐서의 **bitplane / signed-code 레이아웃을 명시적 형식 태그로 분리**, 저장 포맷 버전·재시작·배치·성능 폴백을 검증해야 한다. 현재는 연구 전용 opt-in 코드다.
2. 로짓 기반 텐서별 민감도 추정·자동 최적 정밀도 정책은 별도 연구이며 **이전에 실행 요청이 안전 검사로 차단됐다**. 이 작업을 완료한 것으로 표시하거나 차단을 우회하지 않는다.
3. 실제 LLM 작업 품질/새 독립 IID·OOD/기존 V6 24개 사용 출처 오염·라이선스 검증 전에는 Q를 완성·승격하거나 품질 우위를 주장하지 않는다.
4. CPU Q4G64, 단일·배치 GEMM, Apple Metal GPU, 지속 부하·온도·전력, 모델 외부 데이터로 정밀도 정책을 시험하는 일은 별도 후속 과제다.

**안전/릴리스:** `main`·운영 릴리스·원본 Qwen 체크포인트·XOX 작업 트리 변경 없음. 모든 실행은 EOE 연구용 scratch. 운영 자동 승격 없음.
