# Beglin HCP P6 — AF 로그잇·반복 A/B 실기기 검증 핸드오프

작성일: 2026-10-14 (Asia/Seoul). 실험 종료: 11:18:03 KST. 실행: Tailnet를 통한 XOX 실기기. 이번 P6 결과는 GitHub Actions 실행 결과가 아니다.

## 1. 최종 판정

**P6 계획의 AF 대비 로그잇 직접 비교와 288회 반복 A/B 측정을 완료했다. B의 가속 또는 종합 품질 우위는 입증하지 못했다. 운영 승격은 수행하지 않았다.**

B의 AF 대비 마지막 입력 위치 로그잇 상대 L2 오차 평균은 3.6835%로 A의 4.3498%보다 작았다. 반면 원본 AF와 4토큰 전체 생성 일치는 A 9/12, B 8/12였다. 분포 오차 감소와 생성 시퀀스 보존은 같은 지표가 아니다.

전환·유지 요청을 절반씩 섞은 전체 admission 처리시간에서 B−A 평균은 -1.5936ms, 95% 부트스트랩 구간은 [-7.6850, 4.9634]ms였다. 구간이 0을 포함하므로 가속 증거로 판정하지 않는다.

## 2. 실험 계약과 구현

원본 P5 소스 기반: `b5cf761089153a6326855f267f1381fadb3f414e`. 기존 12개 분야의 동일 SHA 입력을 사용했다. 실제 입력은 106–112토큰, 생성 예산은 4토큰, GPU slot은 1개다.

| 정책 | shared_up_proj / L3 | shared_down_proj / L26 |
|---|---:|---:|
| AF | 원래 AF 바인딩 | 원래 AF 바인딩 |
| A | qNg64 n=6 | qNg64 n=5 |
| B | qNg64 n=5 | qNg64 n=6 |

AF는 원래 양자화된 AF 모델이며 BF16 교사나 사람의 정답이 아니다. 세 정책은 동일한 MLX GPU 네이티브 바이너리에서 실행했다. AF는 비어 있는 promotion map과 실제 STARTUP_STATE ACK, A/B는 기존 Python PrecisionEpochScheduler 및 실제 REBIND_SET_APPLIED ACK를 사용했다. ACK 검증을 모킹하거나 생략하지 않았다.

연구 바이너리에 finalized logits를 읽기만 하는 opt-in 기록 함수를 추가했다. 기본값은 비활성이다. 각 기록의 slot·position·vocabulary·정확한 바이트 수·유한값을 검사한다. 이 함수를 제거하면 검증된 P5 CB128 C 소스와 정확히 일치하고 MLX KV128 소스 SHA도 P5와 같다. 정밀도 연산·라우팅 수식·KV 경계·기존 ACK 코드는 바꾸지 않았다.

로그잇 측정과 속도 측정은 별도 워커에서 순차 실행했다. 속도 측정에서는 로그잇 기록을 끄고 모든 출력의 SHA가 품질 측정과 같은지 확인했다.

## 3. 품질 실측

총 1,315개의 같은 입력 위치에서 어휘 전체 102,400개 로그잇을 비교했다. 생성 이후 문맥이 달라질 수 있으므로 주된 로그잇 오차는 동일한 prefill 문맥에서 계산했다.

|---|---:|---:|
| 마지막 입력 위치 상대 L2 오차 평균 | 4.3498% | 3.6835% |
| 마지막 입력 위치 RMSE 평균 | 0.252223 | 0.215223 |
| 전체 입력 위치 top-1의 AF 일치 | 92.5475% | 93.0038% |

| AF와 4토큰 전체 시퀀스 일치 | 9/12 | 8/12 |

A와 B끼리는 첫 토큰 12/12, 전체 시퀀스 11/12 일치로 P5 관찰을 재현했다. AF 기준으로 energy·language·physics는 두 정책 모두 전체 시퀀스가 달랐다. mathematics는 A가 AF와 같고 B가 달랐다.

각 프롬프트에서 실제 다음 입력 토큰 1,303개를 평가했다. 이것은 해당 입력 텍스트에 대한 next-token 평가이며 질문의 답변 정확도·외부 벤치마크 성능이 아니다.

작은 입력 코퍼스의 기술통계이며 일반적 품질 개선, 비열등성 또는 BF16 대비 정확도를 증명하지 않는다.

## 4. 속도 실측

사전 등록한 6개 시간 블록 × 12개 입력 × 정책별 전환·유지 2종 = 288회 admission을 모두 완료했다. 각 블록은 균형 잡힌 AABB/BBAA 순서를 seed 20261014로 섞었다. 정책마다 전환 72회와 유지 72회다. 별도 warmup 24회와 시작 정책 정렬 44회는 측정 통계에서 제외했다. 6개 블록은 동일 세션 내 반복이지 6대 장비나 6개 독립 실행 세션이 아니다.

주 지표는 Python의 정책 지정 호출 시작부터 반환까지의 admission wall time이다. 스케줄러와 네이티브 전환을 포함하지만 HTTP 또는 원격 네트워크 왕복시간은 아니다. 네이티브 engine wall time에 전환 시간이 이미 포함되므로 더하지 않았다.

| 조건 | A 평균(ms) | B 평균(ms) | B−A 평균(ms) | 95% 구간(ms) |
|---|---:|---:|---:|---|
| 정밀도 전환 | 872.6622 | 871.7006 | -0.9616 | [-11.1628, 10.0192] |
| 정밀도 유지 | 557.7279 | 555.5024 | -2.2255 | [-10.7387, 5.7623] |
| 전환·유지 50:50 | 715.1951 | 713.6015 | -1.5936 | [-7.6850, 4.9634] |

신뢰구간은 12개 입력과 6개 시간 블록을 교차 재표집한 20,000회 부트스트랩이다. 288회를 서로 다른 독립 문제로 취급하지 않았다. 모든 주 비교 구간이 0을 포함한다.

| 혼합 조건의 전체 admission | A(ms) | B(ms) |
|---|---:|---:|
| p50 | 714.9537 | 725.1198 |
| p95 | 906.7799 | 905.1889 |

B는 혼합 조건의 평균이 아주 작게 낮았지만 p50은 오히려 높았다. 단일 중앙값이나 평균만 골라 가속을 주장하지 않는다.

네이티브 전환 비용 자체는 전환 요청에서 평균 A 330.0982ms, B 330.8268ms였다. 이는 정책 간 1–2ms 차이보다 훨씬 크다. 다음 최적화 후보는 잦은 전환 억제, 변경된 정책을 충분히 오래 유지하는 방식, 전환 캐시·동기화 비용 분석이다. 이러한 최적화의 효과를 이번에 구현·입증한 것은 아니다.

## 5. 검증과 운영 보존

신규 측정 도구 테스트 20/20, P5 소스 경계 회귀 6/6, 합계 26/26 PASS. 네이티브 컴파일과 품질·반복 속도 프로세스 모두 exit 0이다. 이는 이번 실행 수치이며 과거 P5 15개 시험과 합산하지 않았다.

별도의 읽기 전용 재계산으로 (블록, 입력, 정책, 전환/유지) 288개 셀이 정확히 한 번씩 있는지, 모든 생성 SHA 일치, admission ≥ roundtrip ≥ engine ≥ transition 관계를 확인했다. 이는 동일 자료의 재검사이며 외부 연구자의 독립 재현이 아니다.

속도 워커의 최대 관측 RSS는 4.387161GiB로 14GiB 한도 이하였다. 품질·속도 전후 운영 바이너리 SHA와 active-route SHA, 운영 네이티브 PID 35481·35493이 동일했다. 연구 워커만 종료했고 운영 워커를 재시작하지 않았다.

이번 작업은 main 병합·배포, Tailnet 릴리스 활성화, 실제 운영 정밀도 변경을 수행하지 않았다. 자동 승격은 수행하지 않았다. 원시 생성 토큰·로그잇은 공개 증거에 포함하지 않고 SHA와 통계만 남겼다. 연구용 원시 로그잇 파일은 측정 후 삭제했으며 최종 조회에서 남은 파일은 0개다.

## 7. Git 소스 보존 사고와 복구

연구 실행 전에는 P5 위에 프로토콜·실행기 커밋을 만들었다. native build 당시 커밋은 `8a81db7724d7c8e4fde41ddf87a92e25079311f1`, 실행기 커밋은 `ef8e4a906f46c25c9e9a6404fe3d4a0393e5b324`였다. 두 값은 당시 preflight에 기록돼 있다.

그러나 CI checkout에 연결한 worktree였고 실행 중 CI checkout이 `0a025b932f6c7563a18a737f64a8f10b189f78e7`로 바뀌었다. 종료 후 연결된 gitdir와 해당 transient commit 객체·브랜치가 사라진 것을 확인했다. 따라서 transient commit을 현재 GitHub에서 조회할 수 있다고 주장하지 않는다.

소스·바이너리·결과 바이트는 남아 있었다. 실행기·측정기·프로토콜을 preflight SHA와 다시 대조한 후, CI에 종속되지 않는 독립 Git clone을 P5 b5cf761 위에서 만들고 정확히 같은 5개 연구 파일과 증거를 옮겼다. 새 보존 커밋은 실행 이후의 아카이브이며 이전 commit 객체 복구와는 구별된다. 상세 기록: `experiments/hcp_p6/evidence/source-preservation.json`.

이후 작업은 CI checkout 또는 깨진 `src` worktree를 사용하지 말고 아래 독립 `repository`에서 새로운 연구용 경로를 준비해야 한다. 이번 실행기에는 연구 경로·SHA가 고정돼 있고 기존 결과 경로 덮어쓰기를 거부하므로 그대로 재실행해 기존 증거를 덮어쓰지 않는다.
